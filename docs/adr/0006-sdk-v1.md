# 0006. Freezing the plugin SDK (v1 candidate)

## Context

By v0.2 seven plugins were written against `@bulig/plugin-sdk`, and the SDK was still `0`: a number that promised nothing. Three things were loose.

- Nothing checked that a plugin does what its manifest says. The kernel refuses an undeclared emit at runtime, but only when that code path runs in production, and it cannot see a declared subscription that is never made, a capability that is declared and never used, or a timer that `stop()` leaves running.
- The contract lived in the code. The event names and payloads that channels and gates rely on were written down nowhere, so a change in one plugin could break another without a test noticing.
- The SDK exported things that are not contract: a glob engine for the scope guard, a zod schema object, kernel helpers.

The roadmap says to freeze the SDK only once real plugins use it, and to pull the API out of working features. That is now possible for some of it and not for the rest.

## Decision

Cut a release candidate, `1.0.0-rc.1`, and write the contract down in `docs/sdk-v1.md`. Each part of the surface is marked stable, experimental or to-remove, and only what has had real use is called stable: the manifest fields, the plugin context, the three capabilities the kernel enforces (`approval.grant`, `merge.request`, `jobs.write`), the stage, approval and cancel events, and the meaning of `merge.refused` against `merge.failed`. Everything with one producer and one consumer (the pipeline and github conversation), the capability names nothing enforces, the stage-name permission convention and the config shape are experimental and say so.

`manifest.sdk` is the major version as a string. The kernel loads majors `0` and `1`. `0` loads with a warning and is removed no earlier than major `2`. The seven plugins in the repo were moved to `"1"` in one mechanical edit, because they all pass the new suite. A breaking change is defined in the doc as anything that would make a stable, previously valid plugin stop working, including a change that needs a plugin less permission than before.

Add a conformance suite at `@bulig/plugin-sdk/conformance`. It runs a plugin in a fake kernel and fails it when the plugin does something its manifest does not say: subscribes, emits and capabilities that differ from the declaration, network, process or file writes with no capability that covers them, `stop()` that throws or leaves a timer, socket or child process behind, an invalid config that is accepted or refused without naming the plugin, and state that is not JSON. Every rule has a test against a deliberately bad plugin. The permission rules in the fake kernel come from the SDK, not a copy: the gated-event map, `jobs.write` and the terminal statuses moved from `@bulig/core` into the SDK so the kernel and the suite read the same source.

The suite blocks side effects instead of watching them. While a plugin runs, network, child processes and file writes are refused. That keeps a conformance run from touching a machine, and it makes the check a tripwire, not a sandbox.

## Consequences

- A new plugin has a checklist it can run before anyone reviews it, and a breaking change to a stable item now has a name and a cost.
- The pass is only as good as the scenarios. A declared event that no scenario reaches is listed as unexercised, not passed. `github` and `worker-claude-code` leave several emits unexercised because reaching them needs a real repo or a real `claude` run.
- The effects check does not stop a plugin that wants to hide an effect, and capability names beyond the three the kernel enforces are still only names. The doc lists this under "Not ready to freeze" so v1 is not read as isolation.
- Marking so much experimental means the freeze is smaller than the name suggests. That is on purpose. The cost is that a third-party plugin that uses an experimental event can break in a minor release.
- The scope helpers in the SDK and the zod schema export are marked to-remove. Moving them is a later, breaking-for-those-imports change that should land before 1.0.0 final.
- The old `sdk: "0"` manifests still work, so a deployment that has not moved sees one warning per plugin and nothing else.
- Release candidate means no third party has used it yet. Expect the first outside plugin to find gaps.
